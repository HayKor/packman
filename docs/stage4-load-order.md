# Этап 4. Порядок загрузки зависимостей

Цель этапа — вывести порядок, в котором должны загружаться зависимости
выбранного пакета, и сравнить результат с реальным менеджером пакетов.

## Реализация

- Ключ конфигурации `load_order: true` включает режим (по умолчанию `false`,
  тогда печатается граф, как на этапе 3).
- Порядок строится итеративным обходом в глубину с пост-обработкой:
  пакет попадает в результат после всех своих зависимостей, поэтому
  зависимости всегда идут раньше зависимых пакетов, а корень — последним.
- Обход без рекурсии, зависимости каждого узла посещаются в лексикографическом
  порядке, что делает результат детерминированным.
- В цикле обратное ребро пропускается, поэтому каждый пакет попадает
  в результат ровно один раз; найденные циклы печатаются отдельной строкой.

Примеры конфигураций: `tests/fixtures/configs/*-order.yaml`.

## Демонстрация на тестовом репозитории

Цепочка `A -> B -> C`:

```console
$ ./run.sh --config tests/fixtures/configs/test-linear-order.yaml

  1. C
  2. B
  3. A
Total: 3 packages

Cycles: none
```

Ромб `A -> B, C; B, C -> D`:

```console
Loading order for A (dependencies first):
  1. D
  2. B

```

Цикл `A -> B -> C -> A` (порядок внутри цикла произволен, цикл показан):

```console
Loading order for A (dependencies first):

  2. B
```

## Сравнение с npm

### Методика

Сравнение выполнялось в отдельном каталоге `/tmp` (в репозиторий ничего
не попадает):

```console
$ npm init -y
$ npm install express@5.3.0
$ npm ls --all --json
$ NODE_DEBUG=module node -e "require('express')"
```

- `npm ls --all --json` даёт дерево установленных зависимостей и версии;
- `NODE_DEBUG=module` показывает фактические загрузки модулей Node.js;
- наше приложение запускалось с `load_order: true` для того же пакета.

### Результаты для `express@5.3.0`

| Показатель | npm / Node | pacman |
|---|---|---|
| Уникальных пакетов | 65 | 68 |
| Записей в дереве зависимостей | 125 | 127 рёбер графа |
| Первый элемент порядка | `express` (запрос загрузки) | `mime-db` |
| Последний элемент порядка | `express` (при обратном обходе) | `express` |

Расхождение по составу ровно одно: `get-intrinsic` установлен как `1.3.0`,
а наш инструмент выбрал `1.3.1`. Из-за этого в нашем графе появились
`async-function`, `async-generator-function` и `generator-function` — все
три объявлены зависимостями `get-intrinsic@1.3.1`.

### Причины расхождений

1. **Выбор версии по диапазону.** npm (`npm-pick-manifest`) сначала проверяет,
   удовлетворяет ли диапазон версия из тега `latest`: если да, берётся она.
   Для `get-intrinsic@^1.2.0` тег `latest` указывает на `1.3.0`, поэтому npm
   устанавливает `1.3.0`, хотя в registry есть более новая `1.3.1`.
   Наш инструмент выбирает наибольшую опубликованную версию, удовлетворяющую
   диапазону, — `1.3.1`.
2. **Разный смысл порядка.** `NODE_DEBUG=module` печатает порядок *запросов*
   на загрузку: первым идёт родительский модуль, затем его зависимости.
   Исполнение модулей завершается в обратном порядке (зависимость
   догружается и выполняется до возврата из `require`), поэтому наш порядок
   «зависимости первыми» соответствует порядку исполнения, а не порядку
   запросов в трассировке.
3. **У Node.js нет единого глобального порядка загрузки.** Модули загружаются
   лениво в момент `require`, условные и динамические импорты меняют порядок;
   трассировка зависит от точки входа.
4. **Дедупликация и hoisting.** npm держит в `node_modules` один физический
   экземпляр пакета на диапазон и переиспользует его для разных родителей.
   Наш граф логический: узел — это `имя@версия`, поэтому при разных диапазонах
   в графе могут оказаться две версии одного пакета.
5. **`package-lock.json`.** Повторная установка npm использует зафиксированные
   версии и не повторяет разрешение диапазонов.
6. **Типы зависимостей.** Мы учитываем только `dependencies`. npm также
   устанавливает `optionalDependencies` и (с npm 7) `peerDependencies`,
   а `bundleDependencies` уже лежат внутри тарбола.

### Маленький пример: `is-odd`

```console
$ npm ls --all
npmcmp@1.0.0 /tmp/opencode/npmcmp
└─┬ is-odd@3.0.1
  └── is-number@6.0.0
```

Наш порядок: `is-number@6.0.0`, затем `is-odd@3.0.1`.
Трассировка Node: `is-odd`, затем `is-number`.
Это та же разница между запросом загрузки и исполнением, что описана выше.

## Обработка ошибок

| Ситуация | Сообщение |
|---|---|
| `load_order` не boolean | `error: parameter 'load_order' must be a boolean ('true' or 'false'), got 'maybe'` |
| цикл в графе | порядок строится, в отчёте строка `Cycles: A -> B -> C -> A` |
| корень под фильтром | `error: package 'A' matches filter 'a', nothing to analyse` |

## Автоматические проверки

- `LoadingOrderCalculatorTest` — цепочка, ромб, цикл, самозависимость;
- `LoadingOrderReportTest` — формат отчёта;
- `GraphCommandTest` — включение режима через конфигурацию;
- `ConfigLoaderTest` — значение по умолчанию, `true` и ошибка типа;
- e2e: четыре сценария на тестовом репозитории, registry-сценарий
  и вывод `--print-config`.
